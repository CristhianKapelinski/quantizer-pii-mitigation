# Engineering Bar — Distinguished-Artifact Level

This repository is held to a **Distinguished-Artifact** quality bar.
Every line of code must be writable as an artifact-evaluation submission
today. There is no "research script vs.
production code" tier here. Hold the bar all the way.

The remainder of this file states the bar. Read it before opening an editor,
revisit it before every commit, and treat divergence from it as a defect.

---

## 1. Reference standards

The standards we conform to are not internal:

- **the venue's artifact evaluation** — Available, Functional, Reproduced, with
  Distinguished signalling clean separation, public hosting, and reviewer
  ergonomics. Plan accordingly: an external reviewer with no prior context
  must clone the repo, follow `README.md`, and obtain the paper's headline
  numbers within a single working session on the documented hardware.
- **the venue's reproducibility guidance** — every numerical claim in the paper
  is regenerated by a script that lives in this repository and is referenced
  from the paper text by file path.
- **ACM Artifact Review and Badging v2.0** — used as a sanity check; aim for
  Reusable + Replicated badges as a side effect of the venue submission.
- **NeurIPS / ML Reproducibility Checklist** — completed and committed as
  `REPRODUCIBILITY.md` at submission time.

Do not invent local conventions when a published one exists.

## 2. Engineering principles

The code is research code. The principles below are **not** waived for that
reason — they are heightened, because research code that survives review,
revision, rebuttal, camera-ready, and post-publication scrutiny lives at
least five years and is read by strangers.

### 2.1 SOLID, DRY, KISS

- **SRP** — one module, one responsibility. Quantization, attack, eval,
  metrics, plotting, and orchestration each live in their own files.
- **OCP** — adding a quantization family or attack variant must require
  *adding* a small file, not editing existing logic. Use a registry pattern
  (`@register("awq")`) when more than two variants share a contract.
- **LSP / ISP / DIP** — subclasses substitute, interfaces stay narrow,
  high-level orchestration depends on abstract loaders/savers, not on
  concrete `transformers` calls. The orchestrator never imports
  `bitsandbytes` directly.
- **DRY** — no copy-paste of canary insertion logic between data prep and
  evaluation; share the helper. If three places sample seeds, factor a
  `_seed.py`.
- **KISS** — three obvious lines beat one clever line. A function that fits
  on one screen with no scroll beats one that doesn't. If a comment needs
  to apologize for the code, rewrite the code.

### 2.2 Design patterns — apply only when they add clarity

Use deliberately:

- **Strategy / Registry** for quantization backends, attacks, decoding
  strategies. Each strategy is a class implementing a small abstract
  interface; selection is data-driven via a config field.
- **Pipeline** for the wave-level orchestration (data → fine-tune →
  quantize → attack → metrics → report). Stages are independent CLI
  entrypoints; the pipeline is a thin shell script that chains them.
- **Builder** for `RunConfig` objects — YAML on disk, dataclass in memory,
  one constructor with explicit defaults.
- **Repository** for adapter / quantized-model artifacts: a single object
  knows where things live on disk, everything else asks it.

Do not import patterns for show. Factories that wrap one constructor,
visitors over flat data structures, and observers in a single-process
script are **noise** — refuse them in review.

### 2.3 QA mindset — write for a senior reviewer

Every change ships with a mental review pass. Before commit, ask:

- **Edge cases** — empty input, single-record input, off-by-one on the last
  batch, mid-epoch checkpoint, zero canaries extracted, empty Poisson lot,
  NaN in logits, OOM mid-iteration, malformed YAML.
- **Logical pitfalls** — silent fallthrough on missing config keys,
  comparing floats with `==`, mutable default arguments, race conditions in
  background eval, integer overflow in step counters, locale-dependent
  string formatting in result tables.
- **Testability** — every pure helper is unit-testable without a GPU; every
  GPU-dependent function has a tiny CPU-only smoke path that exercises the
  control flow.
- **Security** — input from disk is treated as untrusted (no `pickle.load`
  on shipped data, no `eval`, no `shell=True` on untrusted strings, no
  hardcoded secrets, no committed `.env`). Document any exception in
  `THREAT_MODEL.md`.
- **Numerical hygiene** — RNG seeds are explicit and propagated, GPU
  determinism flags are set where reproducibility is claimed, BF16 vs FP32
  choice is justified per call site.

If a category above doesn't apply, say so in the commit message.

### 2.4 Maintainability — the five-year reader

The reader in 2031 has none of your context. They have:

- The `README.md` (current scope, install, smoke).
- The paper PDF and a citation to this commit hash.
- The `EXPERIMENT_MANIFEST.yaml` (every pinned tool version).
- The `PLAN.md` (design rationale and decision gates).
- Git log.

Code must be readable from these alone. Practical implications:

- Module names match what the paper calls them. If §4.3 refers to the
  "Quantization Sensitivity Profile", the file is `qsp.py`, not `metrics_v3.py`.
- Public functions have type hints. No `Any` in user-facing signatures.
- One-line docstrings on public functions; multi-line only when the
  function's contract is non-obvious.
- Configuration is YAML, schema-validated on load, and printed back at
  start of every run alongside the resolved config (defaults filled in).
- Logs are structured JSONL, one event per line, schema documented in
  `experiment/results/SCHEMA.md`.

## 3. Code style

Hard rules, machine-checkable where possible, enforced by `ruff` + `pyright`
in CI:

- **Minimal and concise.** No filler. Prefer comprehensions and small
  helpers over long imperative blocks. Cut every line that does not change
  behaviour or aid the reader.
- **No verbose names.** `lr`, `step`, `cfg`, `q`, `n` are fine in their
  obvious contexts; `learning_rate_for_optimizer_step_within_epoch` is not.
  But also: never `tmp`, `data`, `result`, `obj`. Names describe content
  with the smallest sufficient identifier.
- **No unnecessary print statements.** Production paths log via the
  structured logger. `print` is reserved for entrypoint banners and CLI
  summaries. Strip every `print("here")` before commit.
- **No noisy comments.** Default to writing none. Add one only when *why*
  is non-obvious (a paper reference, a known framework bug, a numerical
  invariant). Never narrate *what* — the code already tells you that. No
  `# TODO` without an issue ID and a date.
- **No dead code.** Delete unused imports, parameters, branches. Commented-
  out code is a defect; the git log is the archive.
- **Imports** ordered stdlib / third-party / first-party, separated by
  blank lines, no wildcards.
- **Functions** under ~50 lines, one return path where possible, raise
  early on invalid input.
- **Constants** at module top, ALL_CAPS, with a short hint of provenance
  (`# Carlini Secret Sharer 2019, §3.2`).

## 4. Reproducibility — the non-negotiable surface

A reviewer must reproduce the paper's headline numbers from a clean
machine in one session. To make that survivable:

### 4.1 Pinning

- Python interpreter version: pinned in `.python-version`.
- All Python dependencies: pinned in `pyproject.toml` with exact versions
  and a committed `uv.lock` (or equivalent).
- System dependencies (`llama.cpp`, `cuda`, GPU driver minimum): named and
  versioned in `EXPERIMENT_MANIFEST.yaml`.
- HuggingFace model snapshots: pinned by **revision SHA**, not tag, in the
  manifest.
- Git commits of every external tool referenced in a wave: pinned in the
  manifest as `<tool>: <commit-sha>`.

### 4.2 Manifest

`EXPERIMENT_MANIFEST.yaml` is the single source of truth for a run. It
includes: tool versions, model SHAs, dataset SHAs, RNG seeds, hyperparams,
hardware fingerprint (`nvidia-smi -q | sha256sum` is fine), and git commit
of this repo. Every run writes a copy of the resolved manifest into its
output directory. The paper's bibliography points at this file.

### 4.3 Determinism

Determinism is on by default in code paths claimed reproducible:

- `torch.use_deterministic_algorithms(True, warn_only=False)`.
- `CUBLAS_WORKSPACE_CONFIG=:4096:8` set in the run launcher.
- `random.seed`, `np.random.seed`, `torch.manual_seed`,
  `torch.cuda.manual_seed_all` all called from a single `seed_everything`
  helper, never per-module.
- DataLoader `worker_init_fn` seeded.
- Document any non-determinism (CUDNN flash-attention paths, stochastic
  decoding) at the call site with a one-line comment naming the source.

### 4.4 The `reproduce.sh` contract

A single `reproduce.sh` regenerates every reported number from shipped
results in under thirty seconds on a CPU-only laptop. A `reproduce_full.sh`
regenerates *everything* — including training — from scratch on the
documented hardware, with a documented runtime. Both scripts are tested in
CI on every PR (the quick path, with golden numbers; the full path on a
nightly schedule when budget permits).

### 4.5 The artifact appendix

Before submission, `ARTIFACT_APPENDIX.md` is filled out using the venue's
template verbatim and kept current with the paper. Reviewer-facing
sections: scope of claims, requirements, set-up, evaluation workflow,
expected runtime per claim. No placeholders at submission.

## 5. Definition of done — per commit

A change is committable when, in this exact order:

1. It does what the commit message says, and only that.
2. No path the change touches has new lint or type errors.
3. The unit tests for the touched modules pass; if behaviour changed, a
   test changed with it.
4. The CPU-only smoke path still runs end-to-end.
5. If a claim in `PLAN.md` or the paper text was affected, it was updated
   in the same commit.
6. The commit message is one short imperative line; the body, if any, is
   wrapped at 72 columns and explains *why*, not *what*.
7. No `Co-Authored-By: Claude` (or any AI co-author trailer). Single human
   author.

If any of those are not true, the work is not done.

## 6. Definition of done — per wave (per `PLAN.md`)

A wave closes when, in this exact order:

1. Every metric the wave's decision gate references is computed and
   committed under `experiment/results/`.
2. The chronological run log has an entry summarising the gate verdict
   with the numerical evidence, signed off with a date.
3. The plan's decision-gate section is updated in place to reflect the
   verdict, and the next wave's open questions are written down.
4. A plot or table that would appear in the paper is generated, even if
   ugly, and saved alongside the data.
5. The `EXPERIMENT_MANIFEST.yaml` for the wave is frozen and tagged
   `wave-<N>-frozen-YYYYMMDD`.

A wave is not closed because training finished. It is closed when the
artifact for that wave can be handed to a stranger and read.

## 7. What "Distinguished Artifact" means here

When the artifact reviewer opens this repo:

- `README.md` first paragraph names the paper, the venue, the contribution
  in two sentences, and the headline reproducibility command.
- The smoke command exits zero in under thirty seconds on a fresh clone
  with `requirements-reproduce.txt` installed.
- Every figure and every table cell in the paper is regenerable from a
  single named command, and the command is printed in the figure/table
  caption (or in a README table mapping caption → command).
- The `LICENSE` is unambiguous.
- The `THREAT_MODEL.md` is concrete enough that a reader can audit whether
  our experimental setup matches the threat model claimed in the paper.
- No artefact from old experiments lingers. No dead code. No commented-out
  paragraphs. The repo reads as if it were written for this submission and
  no other.

That is the bar. It is the bar set by recent Distinguished-Artifact
releases in our space. Hold it from commit one.
