# Not All 4-bit Quantizers Are Equal: Deployment-Time Mitigation of PII Leakage in Fine-Tuned Small Language Models

Reproducibility artifact for the paper of the same title, accepted at SBSeg 2026
([artifact submission instructions](https://doc-artefatos.github.io/sbseg2026/subinstrucoes.html)).
Continuous integration ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs the unit suite and the full offline replay on a clean runner, on every push and weekly, so the 141 published values are re-checked on a machine with none of the authors' state.

**Paper summary.** Four-bit post-training quantization is the default path to deploy small language models. This work shows that the choice of 4-bit quantizer is itself a privacy decision: at the same bit-rate, the calibration-based methods AWQ and GPTQ suppress verbatim extraction of personally identifiable information (PII) memorized during fine-tuning far more than the GGUF k-quant Q4\_K\_M, which uses no calibration corpus. On the primary model, AWQ and GPTQ each reproduce **none** of the planted records while Q4\_K\_M reproduces **5.3%** of them on the same seeds. The effect holds across five open models from 0.5B to 7B parameters and both fine-tuning regimes (full and LoRA), at negligible accuracy cost at production scale.

**What this artifact does.** It re-derives every table and figure of the paper from the committed per-seed logs and checks **all 141 published values** against the paper at its printed precision, in about 7 seconds with no GPU. It also publishes the fine-tuned weights of the headline cell, so the attack can be re-measured from them on any machine.

## Considered Seals
The considered seals are: **Available (SeloD)**, **Functional (SeloF)**, **Sustainable (SeloS)** and **Reproducible (SeloR)**.

- **Available (SeloD)** — public GitHub repository with this README and the complete run of record.
- **Functional (SeloF)** — the *Minimal Test* runs the real analysis pipeline in seconds and prints observable output.
- **Sustainable (SeloS)** — modular package under [`src/qquilt/`](src/qquilt), documented in [`ENGINEERING.md`](ENGINEERING.md), unit-tested with no GPU or network, and every paper claim is traceable to a script and a results directory through [`experiment/results/INDEX.md`](experiment/results/INDEX.md).
- **Reproducible (SeloR)** — `replay.sh` re-derives every table and figure and fails unless all 141 published numbers match the paper exactly; `reproduce.sh` re-runs the pipeline that produced the logs.

**The 37 h figure, exactly.** Summed over the 23 fine-tunes behind `tab:headline`, the
instrumented training is **40.82 h**, of which **3.78 h** are the two A100 cells and
**37.04 h** are the consumer GPUs — and those 37 h are *split across two cards*, 13.81 h
on Machine A and 23.23 h on Machine B, not run on one 16 GB GPU. The 26 committed
fine-tunes together, ablations included, are 45.59 h.

**What the logs do not record, and is therefore not claimed here:** the CPU model, host
RAM and disk of any of the three machines; the Linux *distribution* name and version (the
banner captures the kernel release and glibc version, which is what `platform.platform()`
gives, and nothing else); the NVIDIA driver and CUDA runtime versions actually installed
(the banner stores only a SHA-256 of `nvidia-smi -q`, and the committed logs have that
field redacted for double-blind review); and the provider of the rented A100 pod. The
hostname is redacted for the same reason.

**Timing is instrumented only for fine-tuning.** Quantization, extraction and the analysis
experiments write no timestamps, so this README gives no wall-clock figure for them rather
than an estimate.

**Determinism.** The analysis path is deterministic: `replay.sh` recomputes from fixed logs and the 141 values match exactly, every run, on all three machines above. The *collection* path is not: fine-tuning is not bit-deterministic across GPUs, so a live re-run memorizes a different subset of the canaries and the quantizers then act on a different subset. A re-run reproduces the **direction** of the effect, the calibration-free k-quant leaking more than AWQ, and not the magnitudes. Claim #2 starts from the published weights precisely to skip that step, so everything it does is deterministic on a given machine; it still gates only on the direction, because the extraction counts depend on the CPU the k-quant kernels were built for.

## Dependencies
- **`uv`**, the package manager every command here goes through, and the artifact's only prerequisite. It is not preinstalled on a stock Linux machine and nothing in this repository installs it for you: *Installation* step 0 below is the one-line install, **including the `PATH` step** the installer leaves to you. Once it is there, it fetches its own **Python 3.11** — the version pinned in [`.python-version`](.python-version) — so no system `pip` is used and the PEP 668 *externally-managed-environment* error cannot occur.
- **Python packages**, declared in [`pyproject.toml`](pyproject.toml) and locked to exact versions in [`uv.lock`](uv.lock): torch 2.7.1+cu128, transformers 4.46.3, peft 0.13.2, accelerate 1.1.1, numpy 1.26.4, scipy 1.17.1, statsmodels 0.14.6, matplotlib 3.10.9, and, in the `quant` extra, autoawq 0.2.7 and auto-gptq 0.7.1. Claim #1 exercises only numpy, scipy, statsmodels, matplotlib and click.
- **`llama.cpp`**, built from the commit pinned in [`scripts/build_llama_cpp.sh`](scripts/build_llama_cpp.sh) (CPU-only build, no CUDA). Needed only for Claim #2, which produces the GGUF k-quants. This is the one step that needs **system packages**: `git`, `cmake` 3.14 or newer, and a C/C++ toolchain. The script checks for them and aborts with the missing name rather than failing midway, but installing them first saves a round trip:

  ```bash
  sudo apt-get update && sudo apt-get install -y git cmake build-essential   # Debian, Ubuntu
  sudo dnf install -y git cmake gcc-c++ make                                 # Fedora, RHEL
  sudo pacman -Sy --needed git cmake base-devel                              # Arch
  sudo zypper refresh && sudo zypper install -y git cmake gcc-c++ make       # openSUSE
  ```

  Claim #1 needs none of them.
- **Models and datasets** are public and downloaded from the HuggingFace Hub on first use by the collection path only: Enron (AESLC subset), WikiText-2, Wikipedia (Simple English, 2022-03-01 snapshot), and the backbones Qwen2.5 0.5B/1.5B/7B and Llama-3.2 1B/3B. The Llama backbones are taken from the ungated `unsloth` mirrors, so no `huggingface-cli login` and no accepted licence is needed for any of them, and no paid credential is required. All ids, seeds and hyperparameters are in [`EXPERIMENT_MANIFEST.yaml`](EXPERIMENT_MANIFEST.yaml).

- **Every external download is pinned**, in [`expected/external_artifacts.json`](expected/external_artifacts.json), and the pipeline enforces the pins rather than only listing them:

  | What | Pinned by | Enforced by |
  |---|---|---|
  | HF datasets (Enron, WikiText-2, Wikipedia) | revision SHA | passed to `load_dataset(..., revision=...)` in `qquilt.data`, `qquilt.utility`, `qquilt.groups` |
  | HF backbones (5 models) | revision SHA | passed to `from_pretrained(..., revision=...)` in `qquilt.train`, and recorded in each run's telemetry banner |
  | The two published weight archives | sha256, committed here | `scripts/claim_from_checkpoint.sh` refuses a download that does not match |
  | `llama.cpp` | commit SHA | `scripts/build_llama_cpp.sh` checks it out by SHA and then asserts `HEAD` equals it |
  | The corpora derived from the datasets | sha256 of the committed copies | `qquilt.utility` re-hashes what it rebuilds and stops on a mismatch; the unit suite re-hashes them offline on every run |

  The last row is the one anchored in the campaign rather than in a later observation: `experiment/results/*/utility/enron_holdout.txt` and `wikitext2_ood.txt` were written by the runs that produced the published perplexities, and both are deterministic functions of the upstream dataset, so if Enron or WikiText-2 is ever edited upstream the rebuilt file stops matching and the run **fails** instead of quietly reporting different numbers. To see every pin, and to ask the Hub whether any upstream repository has moved past one:

  ```bash
  python scripts/check_external_artifacts.py            # offline
  python scripts/check_external_artifacts.py --online   # also queries the HuggingFace API
  ```

  What is *not* pinned, and why, is stated in the same file: the campaign recorded no revision at run time, so the revisions are the upstream heads observed on 2026-08-22, each of whose `lastModified` predates the run of record. The three `lm-eval` task datasets and the sentence-transformers encoder have their revisions recorded but not passed, because they are fetched by those libraries and not by this package.

## Security Concerns
Running this artifact poses no risk to the reviewer's machine.

- The PII canaries are **synthetic**, generated by [`src/qquilt/canaries.py`](src/qquilt/canaries.py) from fixed seeds. No real personal data is planted.
- The real-PII experiment uses only the AESLC subset of the Enron corpus, which is already public.
- The pipeline downloads public models and datasets and builds `llama.cpp` from source. It executes no remote code, opens no network service, requires no root, and sends no data anywhere.

## Installation

### Step 0: install `uv` (skip if you already have it)

The environment is built by [`uv`](https://docs.astral.sh/uv/), which is **not**
preinstalled on a stock Ubuntu, Debian, Fedora or Arch machine — the reviewer who prompted
this section had to install it by hand. Check first, before anything else:

```bash
uv --version
```

If that prints a version, go to step 1. If it prints `command not found`, install it:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

The installer puts the binary in `~/.local/bin`, which the **shell you are in right now**
almost certainly does not have on its `PATH`: the installer appends the directory to your
shell profile, and a profile is only read by a *new* login shell. So the very next `uv`
still fails unless you do one of these:

```bash
source "$HOME/.local/bin/env"          # what the installer itself prints; this shell only
export PATH="$HOME/.local/bin:$PATH"   # equivalent, if you prefer to see it explicitly
# or simply: close the terminal and open a new one
```

Then confirm, before going further:

```bash
uv --version                           # must print a version, e.g. uv 0.12.5
```

Two alternatives, if you would rather not run an install script: `pipx install uv`, or
`pip install --user uv` (this one is a Python package, so on a distribution with PEP 668
it needs `pipx` or a virtualenv anyway). Any of the three gives the same `uv`; nothing
below depends on how it was installed.

Together with `git`, `uv` is all the minimal test and Claim #1 need: it downloads its own
Python 3.11 — the version pinned in [`.python-version`](.python-version) — so the system
Python's version does not matter and no system `pip` is used. (Claim #2 additionally needs
`curl`, `tar`, `sha256sum` and a C/C++ toolchain for `llama.cpp`; each script names what
is missing instead of failing midway. See *Dependencies*.)

### Step 1: clone and create the environment

One environment, installed once. Keep the clone and the `cd` on separate lines: chained
with `&&`, a clone that fails because the directory already exists silently skips the
`cd`, and every command after it runs in the parent directory.

```bash
git clone https://github.com/CristhianKapelinski/quantizer-pii-mitigation
cd quantizer-pii-mitigation
uv sync --no-install-project --extra dev --extra quant
bash scripts/build_llama_cpp.sh
```

- **Size and time:** about **7.9 GB**, most of it CUDA wheels, plus a few minutes to
  build `llama.cpp`.
- **A much smaller option for Claim #1 only:** `uv sync --only-group replay` installs
  just the numerics stack (numpy, scipy, statsmodels, matplotlib, click, pytest, about
  120 MB) and skips torch entirely. The minimal test and Claim #1 run under it; Claim #2
  needs the full environment above. This is the environment the CI workflow describes.
- **System packages:** the `llama.cpp` build is the only step that needs them (`git`,
  `cmake` >= 3.14 and a C/C++ toolchain). See *Dependencies* for the command for your
  distribution.
- **No GPU is used by either claim.** The environment is dominated by CUDA wheels because
  the pinned `torch` build is the one the campaign used; everything the claims run is CPU.

>
> **Two claims, both minutes, neither requiring a GPU.**
>
> - **Claim #1** re-derives all 141 published values from the committed logs. Seconds, no

> - **Claim #2** downloads the fine-tuned weights of the headline cell, quantizes them and

### Claim #1: calibration-based 4-bit quantizers suppress verbatim PII extraction that the calibration-free k-quant does not, across 0.5B-7B and both fine-tuning regimes

**Paper reference:** Table `tab:headline`, Table `tab:threefactor`, Figure `fig:story`, and the prose results in `sec:threat-split`, `sec:utility` and `sec:natural-canaries`. This single claim covers every number the paper publishes.

**Verification options (in order of time cost):**

**Option A: numbers only (~1 s).** Checks the 141 published values against the committed logs, without regenerating figures:

```bash
bash replay.sh verify
```

**Option B: full replay (~7 s).** Recomputes the per-seed metrics and the pooled statistics, checks each recomputed field against the committed one, regenerates the paper figure, and then runs the same 141-value check:

```bash
bash replay.sh
```

- **Flags:** none for either option. `bash replay.sh --no-figures` skips only the figure.
- **Expected time:** 2 to 7 s for Option B, measured on three machines (see *Basic Information*).
- **Expected resources:** 200 MB peak RAM, 520 MB of disk for the clone and the environment. No GPU, no network.
- **Expected result:** the five replay stages pass and the run ends with the per-number table and the summary line below. Each row gives where the number is published in the paper, the published value, and the value recomputed from the logs.

```
key                                                       published in    paper    recomputed  status
headline_greedy_ge10_extraction_pct.fullft.qwen0_5b.bf16  tab:headline     30.3          30.3  PASS
headline_greedy_ge10_extraction_pct.fullft.qwen0_5b.q4_k_m tab:headline    23.0          23.0  PASS
headline_greedy_ge10_extraction_pct.fullft.qwen0_5b.awq   tab:headline      0.0           0.0  PASS
...

verify: 141 pass / 0 fail / 0 skip (of 141)

RESULT: OK -- every requested replay stage passed.
```

The script exits non-zero if any recomputed field differs from the committed one or any published number differs from the paper. The same table is written to [`docs/REPRODUCIBILITY_REPORT.md`](docs/REPRODUCIBILITY_REPORT.md).

### Claim #2: the calibration-free k-quant hands over canaries that the calibrated one does not

**Paper reference:** Table `tab:headline`, the Qwen2.5-0.5B full fine-tune row.

**What this runs.** It downloads the fine-tuned weights of that cell from their Zenodo
record ([10.5281/zenodo.22666122](https://doi.org/10.5281/zenodo.22666122), public: no
account, no token), checks the archive against the sha256 committed in
[`expected/external_artifacts.json`](expected/external_artifacts.json) and aborts if it
differs, quantizes the weights to Q8_0, Q5_K_M and Q4_K_M, and runs the extraction attack
against each. With a CUDA GPU it also attacks the published AWQ model, so both sides of
the contrast are measured here; without one, AWQ's side is the paper's number. Same
command either way.

```bash
./scripts/claim_from_checkpoint.sh
```

- **Expected time:** 2 to 8 minutes measured, the download included.
- **Expected resources:** ~4 GB of disk, ~2 GB RAM. Downloads 958 MB, or 1.4 GB on a machine
  with a GPU, which also fetches the AWQ model.
- **Expected result:**

```text
══════════════════════════════════════════════════════════════════
  Claim: the calibration-free k-quant hands over canaries that the
         calibrated quantizer does not
──────────────────────────────────────────────────────────────────
  canaries extracted verbatim             here   paper
  Q8_0                                      30      30
  Q5_K_M                                    28      28
  Q4_K_M  (calibration-free)                24      24
  AWQ 4-bit (calibrated)                     0       0
──────────────────────────────────────────────────────────────────
  GATED: Q4_K_M > AWQ (measured here)                   24 > 0   OK
  counts vary with the CPU build and are not gated
──────────────────────────────────────────────────────────────────
  RESULT: OK   (the contrast the paper claims holds here)
══════════════════════════════════════════════════════════════════
```

- **A warning you should expect.** The quantizer prints
  `WARNING: 144 of 168 tensor(s) required fallback quantization`, and one
  `llama_tensor_get_type` line per tensor above it. Nothing is wrong: this backbone's hidden
  size (896) is not a multiple of 256, which the K-quant block format requires, so
  `llama-quantize` falls back to `q5_0` or `q8_0` on those tensors. It is deterministic, it
  applies identically to the run the paper reports, and the resulting file is the Q4_K_M the
  paper measured.
- **What is gated.** Only the contrast. The counts are reported and not gated:
  `scripts/build_llama_cpp.sh` builds with `-march=native`, so the SIMD kernels differ per
  CPU and a greedy decode resolves a near-tie differently. On one machine the same weights
  and the same GGUF gave 24 canaries with the native build and 21 with a portable one.
  The weights are published precisely because the step before this one, fine-tuning, does
  not reproduce at all across GPUs.

## Cleaning up

